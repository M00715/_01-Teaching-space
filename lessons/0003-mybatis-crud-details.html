Spring Boot CRUD 复习 · 第 3 课 / 共约 6 课 · 预计 25 分钟

🎯 本课服务于 MISSION.md：你第 2 课已经把 Controller → Service → Mapper → DB 的骨架跑通了。现在把骨架里那几行 CRUD 真正吃透——两种写法怎么选、参数怎么传才安全、结果怎么映射回对象、以及怎么证明 CRUD 真的对。

一、两种 Mapper 写法：注解 vs XML

你第 2 课用的是注解式——SQL 直接写在接口方法上。MyBatis 还支持 XML 式（SQL 抽到独立 .xml）。先看清各自适合什么：

注解式（你现在的）

SQL 写在方法上

一个方法旁边就是它的 SQL，直观、短。缺点：SQL 一长、还要动态拼条件就难看，且 IDE 帮不上 XML 的校验。

XML 式

SQL 抽到 UserMapper.xml

接口只声明方法，SQL 写在 resources/.../UserMapper.xml。优点：动态 SQL（<if>/<foreach>）、超长 SQL 好维护、SQL 与 Java 解耦。

// 注解式（简单 CRUD 用这个正好） @Select("SELECT * FROM user WHERE id = #{id}") User findById(Long id); // XML 式：接口只声明 List<User> findByCondition(UserQuery q); // —— 对应的 UserMapper.xml —— <select id="findByCondition" resultType="learn.springboot.entity.User"> SELECT * FROM user <where> <if test="q.name != null"> AND name = #{q.name} </if> <if test="q.age != null"> AND age = #{q.age} </if> </where> </select> # 让 MyBatis 找到 XML（application.yaml） mybatis: mapper-locations: classpath*:mapper/*.xml
📌 怎么选？ 简单 CRUD 用注解（你目前全用注解，正确）；遇到动态条件、超长 SQL 再换 XML。不用一上来就 XML。

二、#{} 和 ${}：一个保命的区别

这是 CRUD 里最容易写出安全漏洞的地方，必须分清：

  • #{name} → 预编译参数占位符。MyBatis 生成 PreparedStatement，用 ? 占位，参数值安全地传入。→ 防 SQL 注入。
  • ${name} → 字符串拼接。把内容直接拼进 SQL 文本。→ 有注入风险，只能用于"表名/列名"这种不能预编译的地方（且必须白名单校验）。

🔧 一个对比就懂为什么 ${} 危险

  1. 安全：WHERE name = #{name} → 实际执行 WHERE name = ?，参数值是 '张三'，无法越界。
  2. 危险：WHERE name = '${name}' → 若有人传入 ' OR '1'='1，SQL 变成 WHERE name = '' OR '1'='1' → 恒为真，整张表被拖走。

你第 2 课骨架里用的全是 #{}，正确。永远优先 #{}，只有当要动态指定表名/列名时才用 ${}，且必须做白名单校验。

三、参数怎么传

// ① 单个参数：名字任意，建议用属性名 @Select("SELECT * FROM user WHERE id = #{id}") User findById(Long id); // ② 多个参数：用 @Param 起名 @Select("SELECT * FROM user WHERE name=#{n} AND age=#{a}") User findByNameAge(@Param("n") String name, @Param("a") int age); // ③ 对象参数：#{属性名} 自动取对象的 getter @Insert("INSERT INTO user(name,age,email) VALUES(#{name},#{age},#{email})") void insert(User user); // ④ 集合参数（IN 查询）：配合 <foreach>（XML 写法） <delete id="deleteByIds"> DELETE FROM user WHERE id IN (<foreach collection="ids" item="id" separator=","> #{id} </foreach>) </delete>

四、结果怎么映射回对象

  • 默认：SELECT 的列名与实体字段名按名字对应（不区分大小写）。你第 2 课的 User(id, name, email) 列名=字段名，所以 SELECT * 直接映射成功。
  • 下划线转驼峰：数据库常用 user_name，Java 用 userName。在 application.yaml 加 mybatis.configuration.map-underscore-to-camel-case: true，MyBatis 自动把 user_name → userName。
  • 显式映射：列名和字段名不一致、又不想开全局驼峰时，用 @Results/@Result（注解）或 <resultMap>（XML）指定 column → property。
# application.yaml 加一行，下划线列自动映射驼峰字段 mybatis: configuration: map-underscore-to-camel-case: true

五、怎么证明 CRUD 真的对 （本节属进阶，可延后）

手写 CRUD 最易错在三处：SQL 拼错、参数名对不上、映射错。两种验证手段：

  • 手动验证（你已会，够用）：curl / Postman 把 5 个端点各跑一遍，看返回。"能写 CRUD"这个目标，靠它就能验证。
  • 自动化测试（进阶·可延后）：@SpringBootTest 启动上下文，@Autowired UserService，插入→查询→断言。测试里加 @Transactional 可自动回滚，不污染数据库。它是一套独立技能，等你 CRUD 写顺了再学完全来得及。
@SpringBootTest class UserServiceTest { @Autowired UserService service; @Test @Transactional // 跑完自动回滚 void create_then_find() { User u = service.create(new User(null, "张三", 20, "z@s.com")); User got = service.findById(u.getId()); assertEquals("张三", got.getName()); // 断言 CRUD 真的对 } }
🧭 别被这段代码吓到——它其实你 90% 都会了
把它和你在第 2 课写的 UserService 对照，只有 4 个新东西，其余全是老朋友：
① @SpringBootTest = "把整个 Spring 应用启动起来"（本就要启动才跑）；
② @Autowired = 你早会的注入，这里注入 UserService/UserMapper；
③ @Test = 打个标记，告诉工具"这个方法请自动帮我跑"（你不用手动调它）；
④ assertEquals(期望, 实际) = "检查两者相等，不等就报错" —— 就是 if 判断的自动化版。
所以整段意思就是：启动应用 → 注入 Service → 存一条 → 查出来 → 检查名字对不对。你平时用 curl 手点，它就是把这套动作写成代码自动跑。

六、动手任务（约 20 分钟）

  1. 给 UserMapper 加一个按名字模糊查询：List<User> findByNameLike(@Param("kw") String kw);，注解写 SELECT * FROM user WHERE name LIKE '%'||#{kw}||'%'（SQLite 用 || 拼接）。
  2. 加一个批量删除：int deleteByIds(@Param("ids") List<Long> ids);，用 XML + <foreach> 写（练 XML 写法，配好 mapper-locations）。
  3. （进阶·可选）写一个 @SpringBootTest 测试：插入一条再查出来，断言 name 相等。不会可以先跳过——它不影响你写出 CRUD，等想学"自动验证"时再回来做。
⚠️ 做第 1 题时必踩的坑：路径冲突 → 500 Ambiguous handler methods
若把模糊查询写成 @GetMapping("/{name}")，它会和已有的 @GetMapping("/{id}") 形状完全一样（都是 /users/{一段}），于是任何 /users/xxx 请求同时匹配两个方法，Spring 无法选择，抛 IllegalStateException: Ambiguous handler methods mapped。
✅ 正确做法：给查询独立路径——@GetMapping("/search") + @RequestParam String name（请求 /users/search?name=张，搜索场景最地道）；或 @GetMapping("/name/{name}")（路径变量形式，参数必须加 @PathVariable，且名字含 / ? & 会破坏 URL，不如查询参数版稳妥）。
📌 顺带三个坑：① URL 里的中文会显示成 %E5%BC%A0，那是正常的百分号编码，不是乱码、也不是错误来源；② findByNameLike 返回的是 List<User>，Controller/Service 的返回类型要和 Mapper 一致，别强转成一个 User（运行期会 ClassCastException）；③ 注解路径别加尾斜杠——@GetMapping("/search/") 在新版 Spring 只匹配带斜杠的 URL，会让你哪怕参数写对也 404；@RequestParam 配 ?name=值、@PathVariable 配 /值，不能混。
