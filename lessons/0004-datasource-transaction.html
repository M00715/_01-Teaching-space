一、连接从哪来：DataSource 与连接池

你第 3 课写的 @Select("SELECT * FROM user WHERE id=#{id}")，MyBatis 帮你执行了 SQL，但它怎么拿到一条到 SQLite 的"数据库连接"的？答案是 DataSource。

DataSource

数据库连接的"工厂/管理员"

Spring Boot 通过它获取连接。你不需要 new 连接，只要注入 DataSource（或直接用 MyBatis 的 Mapper，底层自动借连接）。

HikariCP（默认连接池）

预先养好一批连接，随用随借

启动时建好一批连接放着。请求来了"借"一个 → 用完"还"回去，避免每次请求都现建连接（TCP 握手 + 鉴权很慢）。

# application.yaml —— 这就是给连接池的"配方" spring: datasource: url: jdbc:sqlite:identifier.sqlite username: # SQLite 通常留空 password: # SQLite 通常留空 # （可选）调连接池大小，默认已够用 spring: datasource: hikari: maximum-pool-size: 10 minimum-idle: 2

🔧 一个类比就懂连接池

  1. 没有池：每来一位顾客（请求），餐厅现招一名服务员（建连接）、培训、上岗，顾客走就开除。慢且浪费。
  2. 有池（HikariCP）：提前雇好 10 名服务员待命。顾客来了直接借一名，用完归队。下一桌接着用，几乎零等待。

所以你配的那行 url，是告诉连接池"去哪个数据库、用啥账号"。之后的事（建连、复用、回收）全由 HikariCP 托管，你只管写 Mapper。

二、事务 @Transactional：别让数据"半成功"

单条 SQL 自己就会提交（autocommit）。但真实业务常常是多步操作："给 A 减 100，给 B 加 100"。如果第一步成功、第二步崩了，就会出现钱扣了但没到账——数据不一致。

事务 = 把多个步骤打包成"要么全成、要么全败"的原子操作。
生活例子：转账。A-100 与 B+100 必须同时成功；中途任何一步出错，就回滚到转账前的状态，仿佛什么都没发生。
@Transactional 加在方法上 = "这个方法里的所有 DB 操作，要么一起提交，任一失败就一起回滚"。
@Service public class UserService { private final UserMapper mapper; public UserService(UserMapper m) { this.mapper = m; } @Transactional // ← 这俩更新要么都成、要么都回滚 public void resetTwoUsers(Long id1, Long id2) { mapper.updateAge(id1, 0); mapper.updateEmail(id2, "reset@x.com"); // 若这里抛异常，上面两步自动回滚，数据库保持原样 } }

🔧 为什么事务要开在 Service 层，而不是 Mapper 层？

  1. 粒度问题：一个 Mapper 方法通常就是"一条 SQL"，它本身已经是原子的，再加事务没意义。
  2. 组合在 Service：是 Service 把"多个 Mapper 调用"组合成一个业务动作（如"转账""批量重置"）。事务边界必须圈住这个业务动作，才算"要么全成要么全败"。
  3. 对照你现在的代码：UserController → UserService → UserMapper。你在 UserService 上标 @Transactional，就能罩住它内部调用的所有 Mapper——这正是"事务在 Service 层开"的含义。

🏦 真实案例：转账（你已在本项目 _01 亲手实现）

user 表加了 money 列后，"张三转 50 给里斯"就是最经典的事务场景：扣张三 + 加里斯必须一起成败。下面就是你现在项目里真正的代码。

① Mapper（SQL 写在 XML 里，增量更新，不用先查再算）

// resources/mapper/UserMapper.xml <update id="reduceMoney"> update user set money = money - #{amount} -- 张三 -amount where name = #{fromName} and money >= #{amount} -- 余额不足则 0 行 </update> <update id="addMoney"> update user set money = money + #{amount} -- 里斯 +amount where name = #{toName} </update>

② 接收参数：用 DTO 装起来（前端只传"指令"，不传"结果"）

@Data public class TransferRequest { private String fromName; // 谁转 private String toName; // 转给谁 private Integer amount; // 转多少（不是"最终余额"！） }

③ Service：两步 UPDATE 被 @Transactional 罩住

@Transactional public void transfer(String fromName, String toName, Integer amount) { if (amount == null || amount <= 0) throw new IllegalArgumentException("金额必须 > 0"); int r1 = mapper.reduceMoney(fromName, amount); // 第 1 步：张三 -amount if (r1 == 0) throw new RuntimeException("转出用户不存在或余额不足：" + fromName); int r2 = mapper.addMoney(toName, amount); // 第 2 步：里斯 +amount if (r2 == 0) throw new RuntimeException("转入用户不存在：" + toName); }

④ Controller：转账是"动作"，用 POST

@PostMapping("/transfer") public String transfer(@RequestBody TransferRequest req) { userService.transfer(req.getFromName(), req.getToName(), req.getAmount()); return "转账成功"; }
🔍 亲眼看到回滚：发 POST /users/transfer，请求体 {"fromName":"张三","toName":"王五","amount":50}： 第 1 步张三扣成功（200→150），第 2 步"王五"不存在 → 0 行 → 抛异常 → @Transactional 回滚 → 查库张三还是 200。这就是"要么都成、要么都败"的实体证明。

三、实战回顾与进阶练习（可选）

上面「🏦 真实案例」的转账，就是你在 _01 亲手实现的——你已经跑通了事务的完整闭环：增量 SQL + 余额校验 + DTO 收"指令" + @Transactional 罩两步 + 用"转入人不存在"触发回滚。

想再巩固一次，可把转账泛化成批量重置（更接近后台真实操作）：

  1. 给 UserService 加 @Transactional resetUsers(List<Long> ids)，循环把每个用户 age=0、email="reset@x.com" 后调 update(user)。
  2. Controller 加 POST /users/reset，用 @RequestBody List<Long> ids 收 id 数组（和批量删除同一套路）。
  3. 验证回滚：在循环第 2 轮前 throw new RuntimeException("boom")，发 [1,2,3] 后查库——三个用户都应"没变"。删掉异常即恢复。
📌 先别慌：你现在的每个单条 Mapper 操作默认 autocommit，本来就是各自提交、各自成功，所以"写基础 CRUD"这一步暂时不需要碰事务。本课是让你建立认知——等以后一个接口要"多步改数据"时，知道该在哪加 @Transactional。
