一、问题：你的接口返回"七国八制"

看你现在 UserController 的真实返回值——同样都是 /users 下的接口，前端拿到的是完全不同的形状：

成功时，形状各异

前端每接一个接口都得换写法

POST /users → 返回一个 User 对象
GET /users → 返回 List<User> 数组
POST /users/transfer → 返回纯 String "转账成功"
DELETE /users/{id} → 返回 void（只有 HTTP 状态）
DELETE /users/batch → 返回 int（影响行数）

失败时，更糟

异常"裸奔"出去

转账余额不足抛异常，Spring 默认返回一长串：
{timestamp, status, error, path, message, ...}
字段又多又乱，和上面的成功结构完全不是一回事。前端得为"成功一种解析、失败另一种解析"写两套逻辑。

痛点一句话：前端永远不知道"这次拿到的是对象、数组、还是报错"。解决办法就一个——所有接口，无论成功失败，都返回同一种结构 { code, msg, data }。

二、统一返回体：Result<T>

定义一个泛型包裹类，把"业务数据"塞进 data，再统一带上 code（状态码）和 msg（提示）：

@Data public class Result<T> { private int code; // 业务码：200=成功，非200=失败 private String msg; // 提示信息 private T data; // 真正的数据（任意类型，也可为 null） // 成功：带回数据 public static <T> Result<T> success(T data) { Result<T> r = new Result<>(); r.code = 200; r.msg = "ok"; r.data = data; return r; } // 失败：只带码和消息 public static <T> Result<T> error(int code, String msg) { Result<T> r = new Result<>(); r.code = code; r.msg = msg; // data 保持 null return r; } }

🔧 code / msg / data 的约定

  1. code：业务状态码，不是 HTTP 状态码。200 表示业务成功；失败用 400/500 等自定义语义（如余额不足 = 400）。
  2. msg：给人看的提示，成功可写 "ok"，失败写具体原因（"余额不足"）。
  3. data：成功时放业务数据（一个 User、一个列表、甚至 "转账成功" 字符串）；失败时通常 null。

有了它，前端只要写一套解析：if (result.code == 200) 用 result.data; else 弹 result.msg; —— 成功失败一视同仁。

三、改造 Controller：每个接口都包一层

把原来"直接返回实体/字符串/void"的写法，改成返回 Result<...>，用工厂方法包起来：

// 改前：返回类型五花八门 @PostMapping public User create(@RequestBody User user) { return userService.create(user); } @PostMapping("/transfer") public String transfer(@RequestBody TransferRequest req) { userService.transfer(...); return "转账成功"; } // 改后：清一色 Result<T> @PostMapping public Result<User> create(@RequestBody User user) { return Result.success(userService.create(user)); } @PostMapping("/transfer") public Result<String> transfer(@RequestBody TransferRequest req) { userService.transfer(req.getFromName(), req.getToName(), req.getAmount()); return Result.success("转账成功"); }

注意：delete 原来返回 void，现在可以返回 Result<Void> 或 Result<String>（"删除成功"）。所有接口签名统一了，前端解析逻辑也统一了。

四、全局异常处理：别让异常"裸奔"

上面只解决了"成功时结构统一"。失败时如果 Service 抛异常（如余额不足），Spring 仍会吐默认错误 JSON。用 @RestControllerAdvice 全局拦截，转成我们的 Result：

@RestControllerAdvice // = 全局增强所有 @RestController public class GlobalExceptionHandler { // 捕获所有 RuntimeException（含你转账里的余额不足/用户不存在） @ExceptionHandler(RuntimeException.class) public Result<Void> handleBiz(RuntimeException e) { return Result.error(500, e.getMessage()); } }
🔍 现在转账余额不足，前端拿到的是： {"code":500, "msg":"转出用户不存在或余额不足：张三", "data":null}
和成功时 {"code":200, "msg":"ok", "data":{...}} 同一个结构。前端一套解析通吃成功失败。

🔧 @RestControllerAdvice 是什么

  1. @ControllerAdvice 是 Spring 的"全局增强"：它里写的方法，会对所有 Controller 生效。
  2. 加 @RestControllerAdvice = @ControllerAdvice + @ResponseBody，意思是"拦截后返回的是 JSON（不是跳页面）"——正合 REST API。
  3. @ExceptionHandler(X.class) 指定"捕获哪类异常"。可以写多个方法分别处理不同异常（如参数错用 IllegalArgumentException → 400，其他 → 500）。
