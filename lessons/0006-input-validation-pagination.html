一、问题：脏数据直接进库 / 列表一次全返回

脏数据畅通无阻

现在的 create 接口

create(@RequestBody User user) 直接把客户端 JSON 收成实体。
客户端发 {"name":"","age":-5,"email":"哈哈","money":null} 也能进库——没有任何一道门。

列表不分页

现在的 findAll 接口

findAll() 一把返回全部用户。
用户几千条时，SQL 扫整表、JSON 巨大，既拖慢接口又浪费带宽。真实项目几乎必须分页。

痛点一句话：入口不校验 → 脏数据污染数据库；列表不分页 → 接口又慢又臃肿。两件事都让"能用"的 CRUD 离"完整"还差一步。

二、Bean Validation：用注解在入口挡脏数据

JSR-380 是一套"声明式校验"标准，Hibernate Validator 是它的参考实现。规则写在 DTO 字段上，Spring 在把 JSON 绑成对象时自动帮你查，不必手写 if 判断。

🔧 先加依赖（⚠️ 重要）

Spring Boot 3 起，校验不再是 spring-boot-starter-web 的默认包含项，要单独引：

<!-- 加在 pom.xml 的 <dependencies> 里 --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-validation</artifactId> </dependency>

（你的 _01 现在没这个依赖，不引的话 @Valid 不生效、也不报错——这是最常见的"校验没反应"原因。）

校验要标在入参专用 DTO 上，不要标在实体 User 上——实体还用于"查库回填"，给查出来的对象也加校验会互相打架。新建一个 UserCreateRequest：

@Data public class UserCreateRequest { @NotBlank(message = "姓名不能为空") // String 非空且去空格后非空白 @Size(max = 20, message = "姓名最多 20 字") private String name; @Min(value = 0, message = "年龄不能小于 0") @Max(value = 150, message = "年龄不能超过 150") private Integer age; @Email(message = "邮箱格式不正确") // 内置格式校验 private String email; @NotNull(message = "余额不能为空") // 对象非 null（区别于 @NotBlank 仅限 String） @Min(value = 0, message = "余额不能为负") private Integer money; }

🔧 常用注解对照

  1. @NotNull：任意类型 ≠ null（Integer money 没传就是 null）。
  2. @NotBlank：仅 String，≠ null 且 trim() 后长度 > 0（最常用在 name）。
  3. @Size(min,max)：String/集合的长度范围。
  4. @Min / @Max：数值上下界。
  5. @Email / @Pattern(regexp=...)：格式校验。

关键：光在 DTO 标注解不够，必须在 Controller 参数前加 @Valid 才会真正触发。漏了 @Valid 是第二大坑。

Controller 改造：把 @RequestBody User 换成 @Valid @RequestBody UserCreateRequest，再拷进实体落库：

// 改前 public Result<User> create(@RequestBody User user) { ... } // 改后：@Valid 触发校验 @PostMapping public Result<User> create(@Valid @RequestBody UserCreateRequest req) { User u = new User(); org.springframework.beans.BeanUtils.copyProperties(req, u); // DTO → 实体 return Result.success(userService.create(u)); }

三、把校验失败接进全局异常（呼应第 5 课）

校验没过时 Spring 抛出 MethodArgumentNotValidException。这正是第 5 课全局异常处理的用武之地——不用在 Controller 里 try-catch，在 GlobalExceptionHandler 加一个更具体的处理器即可（越具体越优先，排在 Exception.class 之前）：

@ExceptionHandler(MethodArgumentNotValidException.class) // 比 Exception.class 更具体，优先匹配 public Result<Void> handleValid(MethodArgumentNotValidException e) { String msg = e.getBindingResult().getFieldErrors().stream() .map(f -> f.getField() + ": " + f.getDefaultMessage()) .collect(java.util.stream.Collectors.joining("; ")); return Result.error(400, msg); // 业务码 400 = 参数错误 }
🔍 现在客户端发 name:""，接口返回：
{"code":400, "msg":"name: 姓名不能为空", "data":null}
和成功时、和其他异常完全是同一个 Result 结构。这正是第 5 课"统一结构"的回报——前端不用为校验失败写任何特殊分支。

四、分页：LIMIT/OFFSET + COUNT（最贴合 MyBatis）

分页本质就是两句话：① 只查"当前这一页"的数据；② 再查"总共多少条"好让前端算总页数。手写最透明、零黑盒，最贴合你现在的 MyBatis 栈。

// Mapper：两条 SQL @Select("SELECT * FROM user LIMIT #{size} OFFSET #{offset}") List<User> findByPage(@Param("size") int size, @Param("offset") int offset); @Select("SELECT COUNT(*) FROM user") int countAll();

offset 怎么算？ 第 page 页、每页 size 条 → offset = (page - 1) * size。例：第 2 页、size=10 → 跳过前 10 条，取接下来的 10 条。

再定义一个页结构，把"数据 + 总数"打包（照样包进 Result）：

@Data public class PageResult<T> { private List<T> list; // 当前页数据 private long total; // 总条数（算总页数用） private int page; // 当前页 private int size; // 每页条数 }

Service 组装、Controller 用 @RequestParam 收页码（带默认值，不传也能用）：

// Controller @GetMapping public Result<PageResult<User>> findAll( @RequestParam(defaultValue = "1") int page, @RequestParam(defaultValue = "10") int size) { return Result.success(userService.findPage(page, size)); } // Service public PageResult<User> findPage(int page, int size) { int offset = (page - 1) * size; List<User> list = userMapper.findByPage(size, offset); long total = userMapper.countAll(); return new PageResult<>(list, total, page, size); }

🔧 进阶替代：PageHelper

MyBatis 有个拦截器 PageHelper，一行 PageHelper.startPage(page, size) 就能自动给紧接着的那条查询拼上 LIMIT。好处是 Mapper 不用改 SQL；坏处是"靠线程上下文偷偷改 SQL"的黑盒，调试时不直观。教学阶段建议先手写，把 LIMIT/OFFSET 想明白，再了解 PageHelper 不迟。

五、在 _01 里动手（可选 · 进阶）

  1. 引依赖：在 pom.xml 加 spring-boot-starter-validation（否则 @Valid 静默失效）。
  2. 建 DTO：dto/UserCreateRequest.java，字段标 @NotBlank/@Size/@Min/@Email 等。
  3. 改 Controller：create 用 @Valid @RequestBody UserCreateRequest，拷贝进 User 再落库。
  4. 接异常：在 GlobalExceptionHandler 加 @ExceptionHandler(MethodArgumentNotValidException.class) → Result.error(400, 字段错误)。
  5. 加分页：Mapper 加 findByPage + countAll；建 common/PageResult.java；Service 组装；findAll 改成收 page/size 返回 Result<PageResult<User>>。
  6. 重启验证：POST /users 发 {"name":""} 看返回 code:400；GET /users?page=1&size=2 看返回的 list/total/page/size。
📌 和前两课一样：校验与分页是"生产级规范"，不是 CRUD 的必需功能。你现在的接口"能用"，只是不够严谨。本课是让你知道一套完整 CRUD 还差哪两块拼图。不强制改现有代码。
