一、异常是什么：一种"走不通就往回传信号"的机制

一个方法正常应该 return 一个结果（比如 User）。但运行时可能出意外：参数非法、查库失败、空指针……这时候它没法返回正常的 User，就改为抛出一个异常对象，沿着调用它的地方"往回传"，让上层决定怎么处理。

一句话：返回值是"正常结果"，异常是"意外信号"。异常不是错误本身，而是通知上层"这里出意外了"的载体。

二、异常体系树（必须刻进脑子）

Throwable （所有"可抛"的根） ├── Error 严重到 JVM 级的问题（如 OutOfMemoryError） │ 基本不该你 catch，程序通常也无能为力 └── Exception 程序级、可以也应该处理的意外 ├── RuntimeException 及其子类 → unchecked 非受检（编译不强制处理） │ ├── NullPointerException │ ├── IllegalArgumentException │ └── IndexOutOfBoundsException └── 其它 Exception（IOException、SQLException…） → checked 受检（编译强制处理）

🔧 一个判断口诀

"它是不是 RuntimeException 的子类？"

  • 是 → unchecked（非受检）：编译器不强制你 try-catch 或 throws，你不处理也能编译通过（比如空指针）。
  • 不是 → checked（受检）：编译器强制你必须处理（catch 掉，或在方法上 throws 声明），否则编译不过（比如读文件 IOException）。

记忆点：名字里的"受检"=编译器会 check（检查）你有没有处理它。

三、throw / throws / try-catch-finally 三件套

throw（主动抛）

写在方法体里

throw new IllegalArgumentException("年龄非法");
意思是"这里出意外了，我主动抛一个异常出去"。

throws（声明会抛）

写在方法签名上

void save() throws IOException
意思是"我自己不处理，把处理责任交给调用我的人"。

try-catch-finally（自己接）

就地处理

try{...}catch(Xxx e){...}finally{...}
catch 接住并处理；finally 无论成败都执行（常用来关资源）。

四、异常如何"冒泡"（核心机制，记牢）

方法 A 调 B、B 调 C。若 C 抛了异常又没在 C 里 catch，异常就沿 C → B → A → … 一层层往回传（这叫栈展开 stack unwinding），直到：

  • 某层用 catch 接住了 → 在那里处理，冒泡停止；
  • 一直没人接，传到最顶层（JVM）→ 打印堆栈、程序终止。
关键推论：你 _01 的 Controller 方法里根本没写 try-catch，但异常照样能被统一处理——正是因为异常会一路冒泡到更外层的框架，被框架接住。这就是下一节的主角。

五、为什么 @RestControllerAdvice 能兜住（最重要的一节）

一次请求在 Spring 里的链路是这样的——注意异常在"你没 catch"时怎么被框架接走：

HTTP 请求
浏览器 / Postman
→
DispatcherServlet
Spring 前端控制器
→
你的 Controller 方法
抛异常·没 catch
→
HandlerExceptionResolver
Spring 异常解析器
→
@ExceptionHandler
你写的处理方法
→
Result JSON
统一返回·写回前端

Controller 方法抛异常、你又没写 try-catch → 异常冒泡到 DispatcherServlet → Spring 内置的异常解析器把异常交给匹配的 @ExceptionHandler 方法 → 你 return Result.error(...)，Spring 把它当正常响应写回前端。

这就是"看起来没 catch，却还是被统一处理"的真相：框架在你方法的更外层接住了异常。这是一种 AOP / 横切 思想——不用每个方法都写 try-catch，一处统一兜底所有 Controller。

🔧 最具体优先（决定走哪个 handler）

当存在多个 @ExceptionHandler 时，Spring 选最匹配异常类型的那个。父类能接的，子类也能接；但子类更"具体"，所以优先子类。

例：MethodArgumentNotValidException 既是自身类型、也是 Exception 的子类 → 校验失败时它会被更具体的 handleValid 先接走，不会落到兜底的 handleBiz。

六、对照你 _01 里真实的处理器

你 common/GlobalExceptionHandler.java 里三个方法，正好对应上面三节：

// ① 兜底：接住所有没被更具体处理器捕获的异常 → 500 @ExceptionHandler(Exception.class) public Result<Void> handleBiz(Exception e) { return Result.error(500, e.getMessage()); } // ② 校验失败：比 Exception 更具体 → 优先匹配 → 400 @ExceptionHandler(MethodArgumentNotValidException.class) public Result<Void> handleValid(MethodArgumentNotValidException e) { String msg = e.getBindingResult().getFieldErrors().stream() .map(f -> f.getField() + ": " + f.getDefaultMessage()) .collect(Collectors.joining("; ")); return Result.error(400, msg); // 多个字段错误拼成一个可读串 } // ③ 参数类型不匹配（如 age=4d0）：更具体 → 400 @ExceptionHandler(MethodArgumentTypeMismatchException.class) public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) { Class<?> type = e.getRequiredType(); String typeName = (type != null) ? type.getSimpleName() : "?"; return Result.error(400, "参数" + e.getName() + "收到非法值" + e.getValue() + "，应为 " + typeName); }

记住分工：② 校验失败（参数格式）用 400，③ 类型转换失败（如字符串转数字）也用 400，① 其余一律 500。这正是"客户端错的给 4xx、服务端错的给 5xx"的 HTTP 语义。

七、什么时候该自己 throw（实战心法）

全局处理不是只接框架异常。你自己写业务时也该主动抛：

// 业务规则不满足时，主动抛，让全局处理器统一转成 Result.error public User findById(Long id) { User u = mapper.selectById(id); if (u == null) { throw new IllegalArgumentException("用户不存在: " + id); } return u; // 不抛、只 return null 的话，上层会一脸懵 }

用异常表达"业务意外"，比 return null 清晰得多——上层要么拿到正常结果，要么拿到被统一包装过的错误 JSON。这习惯对你将来写 L1/L2 的 AI 后端同样重要。
